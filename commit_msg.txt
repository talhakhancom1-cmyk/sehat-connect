Admin features: password reset, impersonation, support role, audit logging

#1 Admin Password Reset + Force Change:
- New AuditLog model with actor, action, target, details, IP
- Added must_change_password boolean + permissions JSONB to User model
- POST /api/users/:id/reset-password: generates 16-char temp password,
  hashes it, sets must_change_password=true, emails via SMTP, revokes
  all sessions, logs to audit trail
- POST /api/auth/force-change-password: user must set new password
  before accessing anything else
- AuthContext redirects to /force-change-password if flag is true
- New ForceChangePassword page

#3 Support Role + Permissions:
- requirePermission() middleware checks user.permissions JSONB
- Super_admin bypasses all permission checks
- Permission keys: can_view_users, can_reset_passwords, can_impersonate,
  can_view_tickets, can_view_medical_data
- PATCH /api/users/:id/permissions (super_admin only) to set granular
  permissions per user
- AdminUsers page now shows "Manage" button with password reset and
  impersonation actions (only if user has the permission)

#2 Impersonation:
- POST /api/auth/impersonate/:userId: creates special JWT with both
  admin_id and impersonated user info, 2-hour expiry, logs start
- POST /api/auth/end-impersonation: restores admin token, logs end
- GET /api/auth/audit-logs: admin-only audit log viewer
- ImpersonationBanner component: persistent yellow banner at top
  showing "Impersonating [User] — Admin: [Admin]" with End button
- Cannot impersonate other admins (prevents privilege escalation)
- Cannot impersonate yourself
- Medical data visibility: Support role never sees medical data even
  during impersonation (enforced at route level via can_view_medical_data
  permission). Full admin can see medical data (with audit logging).
- Admin's original token saved in localStorage as ehc_admin_token
  and restored when impersonation ends
